# مرجع 3x-ui برای ماژول ربات Nexora

> این سند از مستندات رسمی 3x-ui استخراج شده و مرجع تصمیم‌های فنی
> ماژول ربات است. قبل از هر تغییری در `xui.py` اینجا را بخوانید.

---

## تغییر معماری مهم — نسخه ۳.۴ به بعد

3x-ui معماری کلاینت‌ها را **کاملاً عوض کرده**:

| | معماری قدیمی (تا ~۳.۳) | معماری جدید (۳.۴+) |
|---|---|---|
| محل ذخیره کلاینت | داخل JSON فیلد `settings` هر inbound | جدول مستقل `client_records` |
| رابطه با inbound | یک کلاینت = یک inbound | یک کلاینت → چند inbound (attach/detach) |
| آمار ترافیک | جدا برای هر inbound | یکپارچه در سطح کلاینت |
| لیست‌گیری | همه‌ی inboundها را می‌گرفتی و پارس می‌کردی | `/list/paged` با فیلتر و صفحه‌بندی |
| به‌روزرسانی زنده | polling | WebSocket (`client_stats`) |

**سرویس‌های مسئول:** `ClientService` و `ClientController`
(`internal/web/service/client_crud.go`, `internal/web/controller/client.go`)

### پیامد برای ما

سرور تولید ما روی **v3.5.0** است، یعنی معماری جدید. ولی `xui.py`
هنوز از endpointهای قدیمی استفاده می‌کند:

```
/panel/api/inbounds/addClient
/panel/api/inbounds/updateClient/{uuid}
/panel/api/inbounds/{id}/delClient/{uuid}
/panel/api/inbounds/getClientTraffics/{email}
/panel/api/inbounds/list
```

این‌ها معمولاً برای سازگاری عقب‌رو حفظ می‌شوند، ولی:

- قابلیت‌های جدید (attach چند inbound، bulk، صفحه‌بندی) در دسترس نیست
- ممکن است در نسخه‌های بعدی حذف شوند
- برای پنل‌های بزرگ کند است (باید همه‌ی inboundها را پارس کرد)

**تصمیم:** `xui.py` باید نسخه را تشخیص دهد و اگر معماری جدید بود از
endpointهای جدید استفاده کند، وگرنه به قدیمی برگردد.

## احراز هویت

دو روش، هر دو روی همه‌ی مسیرهای `/panel/api/*` کار می‌کنند:

**۱. توکن API (ترجیحی)**
```
Settings → Security → API Token
Authorization: Bearer <token>
```
مزیت: قابل ابطال بدون تغییر رمز پنل.

**۲. لاگین با کوکی**
```
POST /login  {username, password}
→ کوکی نشست
```

## مدل داده‌ی کلاینت

| فیلد | توضیح | نکته |
|---|---|---|
| `id` / `password` | UUID برای VLESS/VMess، رمز برای Trojan/SS | بسته به پروتکل |
| `email` | شناسه‌ی یکتا | بدون `/`, `\`, فاصله |
| `subId` | شناسه‌ی اشتراک | یکتا؛ لینک ساب از این ساخته می‌شود |
| `totalGB` | سهمیه به **بایت** | `0` = نامحدود |
| `expiryTime` | timestamp **میلی‌ثانیه** | `0` = بدون انقضا؛ منفی = شروع تاخیری (روز) |
| `limitIp` | سقف IP همزمان | با Fail2ban اعمال می‌شود |
| `reset` | چرخه‌ی ریست ترافیک (روز) | `0` = بدون ریست خودکار |
| `enable` | فعال/غیرفعال | |
| `tgId` | آیدی تلگرام | برای اتصال به ربات مفید است |

### اعتبارسنجی که خود پنل انجام می‌دهد

- `hasForbiddenClientChar` — کاراکترهای ممنوع در email و subId
- بررسی یکتایی email و subId هنگام ساخت

**پس ما هم باید قبل از ارسال، همین‌ها را چک کنیم** تا خطای مبهم نگیریم.

## عملیات کلیدی (معماری جدید)

```
GET    /list/paged          لیست صفحه‌بندی‌شده با فیلتر
POST   /                    ساخت کلاینت
POST   /bulkCreate          ساخت انبوه (با الگوی پیشوند/شماره)
POST   /bulkAdjust          تغییر انبوه سهمیه یا انقضا
POST   /attach              اتصال کلاینت به inbound (AttachByEmail)
POST   /detach              جدا کردن
POST   /bulkAttach          اتصال انبوه
POST   /bulkDetach          جدا کردن انبوه
```

فیلترهای `/list/paged`: ایمیل، پروتکل، inbound، بازه‌ی مصرف، وضعیت انقضا

## نکات عملیاتی

**آستانه‌ی دیسپچ نود:** اگر بیش از `nodeBulkPushThreshold` (پیش‌فرض ۵۰)
کلاینت تغییر کند، پنل به‌جای تک‌تک gRPC، نود را «dirty» علامت می‌زند و
یک reconcile کامل می‌فرستد. برای ما یعنی: عملیات انبوه بهتر از حلقه است.

**چندنودی:** پنل می‌تواند چند سرور را مدیریت کند. اگر مشتری ما چندنودی
باشد، باید مشخص کنیم کانفیگ روی کدام نود ساخته شود.

**دیتابیس:** SQLite (پیش‌فرض، `/etc/x-ui/x-ui.db`) یا PostgreSQL.

**سرویس اشتراک:** `sub.Server` و `sub.LinkProvider` — لینک ساب را خود
پنل می‌سازد، ما نباید دستی بسازیم.

**ربات داخلی 3x-ui:** پنل خودش یک ربات تلگرام دارد (کتابخانه‌ی `telego`)
برای مانیتورینگ. ربات ما جداست و نباید با آن تداخل کند — مخصوصاً اگر
مشتری هر دو را با یک توکن راه بیندازد، تلگرام اجازه نمی‌دهد.
**باید در مستندات هشدار بدهیم: توکن ربات باید متفاوت باشد.**
